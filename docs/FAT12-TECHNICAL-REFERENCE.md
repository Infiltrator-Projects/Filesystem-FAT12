# FAT12 original-format technical reference

## Historical lineage and media profiles

This integrated reference describes native media structures, historical compatibility profiles and independent implementation requirements. The cited original specifications remain authoritative.

Marc McDonald's 8-bit allocation-table work for Microsoft/NCR dates to 1977-78; the initial NCR machine is disputed. Standalone Disk BASIC-80 used 16-byte directory records, 6.3 binary names, record-granularity lengths and no subdirectories. MIDAS used 32-byte records. Tim Paterson's QDOS 0.10 (1980) expanded allocation links to 12 bits, used two FAT copies and 8.3 names. 86-DOS 0.42 (February 1981) changed directory records to 32 bytes. PC DOS 1.0 (1981) and MS-DOS 1.25 (1982) spread the format. DOS 2.0 introduced the BPB, hierarchy and additional attributes. Early DOS 1.x disks without a BPB need explicit geometry; do not accept them by label alone. The early 8-bit and 16-byte-directory layouts are separate historical profiles, not silently supported by a modern FAT12 decoder.

## Floppy and OEM geometry

Examples at 512 bytes/sector: 160 KiB (40 tracks, 1 head, 8 sectors/track; media FE); 320 KiB (2 heads, 8 sectors; FF); 180 KiB (1 head, 9 sectors; FC); 360 KiB (2 heads, 9 sectors; FD); 1200 KiB (80 tracks, 2 heads, 15 sectors; F9); 720 KiB (80, 2, 9; F9); 1440 KiB (80, 2, 18; F0); 2880 KiB (80, 2, 36; F0). Media ID alone is ambiguous. A standard 1440 KiB example uses 2880 sectors, 1 reserved, 2 FATs of 9 sectors, 224 root entries and 1 sector/cluster: root=14 sectors; first data=33; 2847 clusters. Apricot uses BPB at 0x50 on certain 315/720 KiB disks. BBC Master 512 DOS Plus uses special 800 KiB/1024-byte and 640 KiB/256-byte formats; the latter has an ADFS boot area. DEC Rainbow 100 uses reserved tracks, no standard BPB and interleave. These need separately validated profile decoding; do not guess. OEM larger logical sectors and partition types 0x08, 0x11, 0x14, 0x24, 0x56, 0xE5 and 0xF2 are historical conventions, not unique format identifiers.

## Packed allocation links and limits

Entry n starts at n+floor(n/2). Read a little-endian 16-bit window, including a second sector if necessary. Even n: window & 0xFFF; odd n: window >> 4. Write even: (old & 0xF000) | value; odd: (old & 0x000F) | (value << 4). Example: entries 0x123 and 0xABC encode bytes 23 C1 AB. Serialise overlapping read/modify/write windows and preserve neighbouring nibbles. Free=0x000; reserved=0x001; ordinary links 0x002..0xFEF; reserved 0xFF0..0xFF6; bad=0xFF7; end=0xFF8..0xFFF. FAT[0] contains media byte plus high ones; FAT[1] usually 0xFFF. No FAT16/32 clean-shutdown bits in standard FAT12. The type cutover allows 1..4084 data clusters; compatibility near reserved values and 4085 cutover requires conservative formatting, not allocating marker-valued IDs. Some DOS versions treat 0xFF0 as EOC. At 4 KiB clusters data area is at most 15.953125 MiB by count; 8 KiB clusters about 31.91 MiB. Larger clusters are special compatibility profiles. File length field is 32 bits on modern directory layout, but usable volume size limits actual files. MBR type 0x01; unpartitioned media has no partition ID.

### Packed links and boundary update

Cluster n has FAT byte offset floor(3*n/2). Read the two-byte little-endian window, take low 12 bits for even n and high 12 bits for odd n. Example: entries 2=0x345 and 3=0xABC occupy bytes 45 C3 AB at offsets 3..5. Replacing entry 2 with 0x789 changes those bytes to 89 C7 AB, preserving the neighbouring entry. If the window straddles a sector, acquire and validate both sectors. Synchronise overlapping updates; two different entries may share a byte. Classify 0 as free, 0xFF7 bad, 0xFF8..0xFFF EOC, 0xFF0..0xFF6 reserved. Reject cluster 1 and out-of-geometry links. Keep FAT copies consistent according to the selected native profile.

## FAT12/FAT16 extended BPB and profiles

For DOS 4.x-style FAT12/16 EBPB: hex offset:size 0x24:1 drive, 0x25:1 reserved, 0x26:1 signature (usually 0x29), 0x27:4 volume ID, 0x2B:11 volume label, 0x36:8 type string; boot code follows. These fields are not present in all older disks. DOS 2.0 introduced core BPB fields; DOS 3.0 introduced further geometry and DOS 3.31 established 32-bit sector-count/hidden-sector fields. Some older disks use alternate boot placement or no valid BPB. Distinguish normative modern layout from each historic profile. Do not interpret historical EA data at directory offset 0x14 as FAT32 high cluster bits. Root entries are fixed at format time; root occupies ceil(32*root_entries/bytes_per_sector) logical sectors. Validate FAT copies before reading/writing.

## Common BPB and region arithmetic

Hex byte offset:size (modern DOS/EFI layout): 0x00:3 jump; 0x03:8 OEM name; 0x0B:2 bytes/sector; 0x0D:1 sectors/cluster; 0x0E:2 reserved count; 0x10:1 FAT count; 0x11:2 root entries; 0x13:2 TotSec16; 0x15:1 media; 0x16:2 FATSz16; 0x18:2 sectors/track; 0x1A:2 heads; 0x1C:4 hidden sectors (DOS 3.31 layout); 0x20:4 TotSec32. Boot signature bytes 55 AA at 0x1FE. The Microsoft EFI profile specifies logical sector sizes 512, 1024, 2048 or 4096 bytes and sectors/cluster 1, 2, 4, 8, 16, 32, 64 or 128. For broad compatibility its cluster size must not exceed 32 KiB; larger or older nonstandard geometries need explicit profiles. FATSz16 and RootEntCnt must be nonzero; FAT32-only BPB fields must not be read as valid FAT12/16 metadata. Use checked arithmetic. root_sectors=ceil(root_entries*32/B); fat_sectors=FATSz16 if nonzero else FATSz32; total=TotSec16 if nonzero else TotSec32; first_data=reserved+FAT_count*fat_sectors+root_sectors; cluster_count=floor((total-first_data)/sectors_per_cluster). Reject overflow, underflow, truncated media and FAT capacity below cluster_count+2 entries. Cluster n sector=first_data+(n-2)*sectors_per_cluster, relative to volume; add partition offset only in whole-device host translation. CHS translation is historical: LBA=((cylinder*heads)+head)*sectors_per_track+sector-1. FAT type is based on count, not the textual label or partition ID. On GPT media the Microsoft basic data GUID is EBD0A0A2-B9E5-4433-87C0-68B6B72699C7; it is shared with other formats. Stay at least 16 clusters away from type cutovers when formatting for broad legacy compatibility.

### Worked floppy geometry

For a standard 1.44 MiB disk with 512-byte sectors, 2880 sectors, one reserved sector, two nine-sector FATs and 224 root records, root directory sectors = ceil(224*32/512)=14. FAT copies begin at sectors 1 and 10; root starts at 19; first data sector is 33. There are 2847 data clusters at one sector per cluster; cluster 2 starts at sector 33 and cluster 2848 at sector 2879. The FAT has floor(9*512*2/3)=3072 packed entries, so capacity exceeds the 2847 data clusters plus two reserved entries. The unused tail cannot be allocated. For a disk with no BPB, an explicit proven historical geometry is required.

## Directory record - exact 32-byte layout

Hex offset:size: 0x00:11 OEM short name (8 base + 3 extension, spaces padded); 0x0B:1 attributes; 0x0C:1 NT case flags (base lowercase bit3, extension bit4); 0x0D:1 create 10ms increment (0..199); 0x0E:2 create time; 0x10:2 create date; 0x12:2 last access date; 0x14:2 first-cluster high word on FAT32, reserved or historical EA handle on FAT12/16; 0x16:2 modification time; 0x18:2 modification date; 0x1A:2 first-cluster low word; 0x1C:4 file size. Attributes: 0x01 read-only, 0x02 hidden, 0x04 system, 0x08 volume, 0x10 directory, 0x20 archive; 0x0F identifies LFN; upper bits reserved. First byte 0x00 means end, 0xE5 deleted, 0x05 encodes initial OEM 0xE5. Directory sizes are normally zero in their entries; derive chain length by traversal. Microsoft specifies a maximum directory storage size of 2 MiB (65,536 records, not files); the fixed FAT12/16 root has a separate BPB-defined limit. Dot points to self; dot-dot uses zero for root parent. Root volume labels are metadata, not ordinary files. Timestamp date bits 0..4 day, 5..8 month, 9..15 year minus 1980; time bits 0..4 seconds/2, 5..10 minute, 11..15 hour. Representable years 1980..2107; historic DOS API often limited to 2099. Access date granularity one day; modification 2s; create increments 10ms where supported. No stored timezone in classic FAT. Preserve unknown/reserved fields as applicable to explicit profiles.

## VFAT long filenames and aliases

VFAT is an optional directory extension to FAT12/16/32, not a separate allocation format. Windows NT 3.5 and Windows 95 adopted long names. Each LFN entry: 0x00:1 ordinal (0x40 marks last logical fragment, physically first); 0x01:10 five UTF-16 units; 0x0B:1 attr=0x0F; 0x0C:1 type=0; 0x0D:1 short-name checksum; 0x0E:12 six units; 0x1A:2 zero first cluster; 0x1C:4 two units. At most 20 records and 255 code units, physical sequence descends to 1 then short entry. Partial final fragment ends with 0x0000 then 0xFFFF padding; full fragment need not include terminator. Checksum over all 11 padded short-name bytes: start s=0, for each b set s=((s>>1)|(s<<7))+b modulo 256. Validate ordinal, checksum, terminator, padding and UTF-16; if invalid, expose only valid short alias or fail according to corruption policy, never fabricate a long name. Alias generation and collision handling are implementation/OS-specific. Preserve associated LFN records through rename/delete and detect orphaned entries. Historical UCS-2 terminology differs from UTF-16 surrogate handling. Short-case bits do not encode arbitrary mixed case.

## Historical extensions, metadata and derivatives

Classic FAT has no native ACLs, resource forks, compression, encryption or general transaction journal. DR-DOS, FlexOS and related multiuser DOS products implemented security extensions; SuperStor, Stacker, DoubleSpace and DriveSpace historically supplied volume compression; DR-DOS supplied optional volume encryption. These are separate compatibility profiles, not baseline capabilities. OS/2 FAT12/16 stores EAs in hidden EA DATA. SF referenced by directory field 0x14; FAT32 uses that word for cluster high bits, so FAT32.IFS uses separate EA. SF sidecar files and marks at 0x0C instead. Macintosh PC Exchange used FINDER.DAT and RESOURCE.FRK; macOS uses AppleDouble ._ files and .DS_Store; UMSDOS used --linux-.---. These are host conventions, not native FAT streams. DELWATCH pending-delete and IBM 4680/4690 distribution attributes repurpose fields; avoid writing unknown extensions. Human68K 18.3 names, TFAT and OEM variable root variants require independent profiles. FATX (Xbox 2001) uses incompatible boot and 64-byte directory records; Turbo FAT is a NetWare derivative. FAT+ draft (2007) is not baseline FAT16/32. Do not claim support or silently reformat any of these formats.

## Allocation, recovery and qualification

No general journal: mirrored FAT copies are not proof of atomicity. Build a reference map from valid directory trees, follow bounded chains, compare expected ceil(file_size/cluster_size) to actual allocation, distinguish zero-length files and directories, detect cycles, cross-links, orphan clusters, bad markers and inconsistent mirrors. Validate target identity and exact source bytes before relocation, reserve new clusters, copy and verify data, publish new links/reference and flush before freeing old allocation; interruption recovery must be explicitly designed and tested. Never run recovery against a guessed target. Free-space scans are linear; allocation hints, contiguous reservation, caching and multi-sector I/O can reduce fragmentation and metadata reads. Slack is unused tail space inside allocated clusters, distinct from external fragmentation. Formatting must solve FAT capacity and root geometry together, not merely write a type string. Test exact boundary counts, sector straddles, odd/even links, malformed BPBs, directory capacity, LFN collisions and corruption, full disks, truncated media, I/O failures and interrupted relocation. Historical recovery and undelete (0xE5) cannot guarantee content remains intact.

### Namespace and independent mutation design

For ordinary file creation, validate the parent directory and name, reserve the required directory slots and data allocation, initialise content, then publish the directory reference. For growth, reserve additional clusters before publishing a longer chain and file length; for shrink, remove reachability before releasing the tail. Rename must preserve object metadata and avoid collisions; moving a directory additionally requires validating its parent relation. Deletion marks namespace entries unused and retires allocation only after references are removed. These are conservative engineering ordering rules, not a guarantee of native crash-atomic operations. Flush ordering, exclusive media ownership, torn-sector behaviour and independently checked recovery must be tested. Never infer a safe writer from a reader or from a successful format operation.

### Forensic and relocation exercises

Construct independent disposable images for empty, exact-cluster, partial-cluster, fragmented and maximum-name files. Record the original directory identity, logical size, allocated cluster list and file hash. Build a reverse ownership map and detect loops, cross-links, lost allocations, bad/reserved clusters, invalid name sets and inconsistent copies. For relocation reserve a destination, copy and compare data, publish the new mapping and release old storage only after durability. Simulate interruption after every phase and compare with native checker output. Distinguish bytes logically visible from allocation slack. Preserve native timestamps, name aliases, attributes and directory identity; do not repair a conflicting allocation by assuming the first claimant is correct.
